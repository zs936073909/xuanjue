# 玄决 · 云端账号体系与后端方案

> 目标：在保持「本地优先 / 隐私优先」的前提下，让「案例、复盘、对话、个人信息」可跨设备同步。
> 账号体系已定为**纯令牌模式**（无邮箱、无手机号、无短信，注册完全免费）；找回用「令牌前 6 位 + 恢复口令」换发新令牌，并通过 `recovery_blob` 取回能解密数据的密钥。
> 本文反映 2026-10-08 实现后的现状：Fastify + PostgreSQL 后端（`server/`）+ 客户端 `js/cloud.js`（端到端加密同步 SDK）。部署步骤见 [免费部署方案](file:///workspace/xuanjue/docs/免费部署方案.md)。

---

## 0. 先说结论（选型）

| 维度 | 方案 |
|---|---|
| **账号体系** | 纯令牌：用户自选 16–64 位同步令牌；服务端只存 `SHA-256(token)` + 前 6 位前缀。JWT 双 token（access 15min / refresh 30d） |
| **找回** | 令牌前 6 位 + 恢复口令 → 换发新令牌 + 返回 `recovery_blob`（恢复口令包裹的数据密钥） |
| **数据加密** | `PBKDF2(同步令牌, kdf_salt)` → AES-256-GCM 数据密钥；服务端只见密文（零知识） |
| **存储** | PostgreSQL（结构化），无对象存储 |
| **同步策略** | 本地优先 + 服务端密文副本 + 乐观并发（`base_rev`，落后 409 重拉）。不做 OT/CRDT，理由见 §6 |
| **部署** | Render / Koyeb 免费 Web 服务 + **Neon 免费 PostgreSQL**（Render 自带免费库 30 天删除，不可用于备份产品） |
| **成本** | 免费档即可跑通；$0/月。只有超出免费额度或要免冷启动才需要付费 |

**一句话**：注册功能本身零成本（没有邮箱/短信/OAuth 任何第三方依赖），要花钱的只有机器和数据库，而这两者都有免费档。

## 1. 为什么需要后端，以及到底要同步什么

当前 `Store`（[store.js](file:///workspace/xuanjue/js/store.js)）把 7 类数据压在 localStorage：

| 键 | 内容 | 同步价值 | 敏感度 |
|---|---|---|---|
| `xuanjue_cases` | 案例 + 复盘 | ⭐⭐⭐ 最高（核心资产） | 高（含问题原文、判断） |
| `xuanjue_chats` | AI 多轮对话 | ⭐⭐ 高 | 高（含出生信息、私事） |
| `xuanjue_profile` | 昵称/出生/性别/地域 | ⭐⭐ 高 | **极高（出生时刻）** |
| `xuanjue_settings` | 偏好 | ⭐ 低 | 中（**含 API Key，绝不上云**） |
| `xuanjue_important` | 重要事项 | ⭐⭐ | 中 |
| `xuanjue_remind_state` | 提醒去重 | 无（设备相关） | 低 |
| `xuanjue_lock` | PIN/指纹/加密态 | **不同步**（每设备独立） | 极高 |

**同步 = cases / chats / profile / important 四类**（`SYNC_KINDS`）。settings 里的 AI Key 永远留在本机。

本期实现范围：以上四类全部同步 + 恢复口令找回 + 多设备列表 + 账号注销。

## 2. 架构

```
┌────────────────────────┐          ┌──────────────────────────┐
│  App（Capacitor WebView）│          │  自建后端（Node/Fastify）  │
│                        │          │                          │
│  Store（本地权威）       │  HTTPS   │  Fastify + JWT           │
│   ├─ cases             │◄────────►│  PostgreSQL              │
│   ├─ chats             │  密文同步  │  ┌─ users                │
│   ├─ profile           │          │  │  ├─ token_hash(sha256) │
│   └─ important         │          │  │  ├─ token_prefix(6)    │
│  Cloud（js/cloud.js）   │          │  │  ├─ kdf_salt          │
│   ├─ 令牌派生数据密钥    │          │  │  ├─ recovery_code     │
│   ├─ AES-GCM 信封加密   │          │  │  ├─ recovery_hash     │
│   └─ 冲突标记/重试      │          │  │  └─ recovery_blob     │
└────────────────────────┘          │  ├─ devices              │
                                    │  ├─ snapshots            │
本地权威（Local-first）：UI 永远读本地；│  ├─ ops（操作日志/增量）   │
云端是「备份 + 跨设备搬运工」。          │  └─ audit_log            │
                                    └──────────────────────────┘
```

设计原则：

1. **离线可用**：没网时所有功能正常，写入本地并标记 dirty，联网后补传。
2. **服务端不碰明文**：账号侧只有令牌哈希；业务数据是密文 blob。
3. **不做实时协作**：单用户多设备，不需要 OT/CRDT。
4. **令牌既是账号也是解密口令**：这是"免费"的根源 —— 没有邮件/短信链路，也就没有任何可计费环节。代价是**令牌丢了且恢复口令也丢了 = 数据永久无法解密**，UI 已用醒目警示说明。

## 3. 数据库 Schema

以 [server/schema.sql](file:///workspace/xuanjue/server/schema.sql) 为准（含邮箱→令牌模式的幂等迁移）：

```sql
CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  token_hash    text NOT NULL unique,        -- 同步令牌的 SHA-256 哈希（不可逆）
  token_prefix  text not null,               -- 令牌前 6 位，找回时定位候选账号
  kdf_salt      bytea not null,              -- 客户端派生数据密钥用
  recovery_code text,                        -- 找回口令（可读，仅用于身份确认）
  recovery_hash text,                        -- 找回口令 SHA-256
  recovery_blob bytea,                       -- 恢复口令包裹的数据密钥，服务端无从解包
  created_at    timestamptz not null default now(),
  last_seen_at  timestamptz
);
-- devices / snapshots / ops / audit_log 见 schema.sql
```

**关键点**：`kdf_salt` 不是机密，注册时就已返回给客户端；但它必须公开 —— 客户端要靠它从令牌派生出数据密钥，否则云端密文解得开而没有钥匙。

**找回为什么能解密**：`recovery_blob = AES-GCM(恢复口令派生的包裹密钥, nonce, 数据密钥)`。服务端只寄存这 32 字节团。找回成功后原样返回，客户端用恢复口令解包拿到数据密钥，才能解密真正同步的数据 —— 否则找回只能重新授权、数据仍然打不开。

## 4. 接口（REST，全部 HTTPS + JWT）

以 `server/routes/` 为准：

```
POST   /v1/auth/register       {token, recovery, recovery_blob, deviceName} → {userId, kdf_salt, recovery_code, access, refresh}
POST   /v1/auth/unlock         {token, deviceName}                          → {userId, kdf_salt, access, refresh}
POST   /v1/auth/refresh        {refresh}                                    → {access, refresh}
POST   /v1/auth/logout         {refresh}
POST   /v1/auth/recover        {prefix, recovery, deviceName}               → {userId, kdf_salt, recovery_blob, access, refresh}
POST   /v1/auth/reset-recovery {token, recovery, recovery_blob}

GET    /v1/me                                                              → {user, devices, snapshots}
DELETE /v1/me                                                              → 级联删除账号

GET    /v1/sync?since=<ts>                                                 → {snapshots:[{kind,ciphertext,nonce,rev,updated_at}], ops:[...]}
PUT    /v1/sync/:kind?device=<name>   {ciphertext, nonce, base_rev}         → {kind, rev}   (409 = 需要先 pull)
DELETE /v1/sync/:kind                                                      → 云端清空该类数据
```

**同步协议（拉-改-推）**

1. `GET /v1/sync?since` 拿云端 rev 与本机对比
2. 本地与云端按 `kind` 分别取 `max(rev)`
3. 推送带 `base_rev`，服务端校验；版本落后返回 `409 rev_conflict`，客户端合并后重试
4. 冲突按 `kind` 取更新者（单用户场景下即为 last-write-wins）

**限速与锁定**：全局 120 次/分钟/IP；登录按 `IP + 令牌哈希前 8 位` 双维度限速，`refresh` jti 黑名单在登出/找回后即时失效。

**`kdf_salt` 契约**：`/register`、`/unlock`、`/recover` 三处都返回，集成测试锁定。

## 5. 客户端改造点

现状（已实现，测试全绿）：

```
js/store.js     ← 本地权威层 + 写钩子 markDirty()
js/cloud.js     ← E2EE、令牌派生、同步队列、token 刷新、冲突重试、找回解包
js/app.js       ← 我的页云同步卡（四态）+ 六个弹窗流程 + 2 分钟周期同步
```

云同步卡的四个状态由 `Cloud.status()` 单一来源驱动：

| 状态 | 界面 |
|---|---|
| `noconfig` | 未填服务器地址（隐私说明） |
| `idle` | 创建令牌（免费）/ 用令牌登录 / 找回 / 换服务器 |
| `locked` | 令牌解锁 / 找回 / 换服务器 |
| `ready` | 上次同步时间 + 立即同步 + 退出 |

**不上传清单**：`settings.aiApiKey`、`lock.*`、`remind_state`。令牌本身也**不落在 DOM 或 storage** —— 只在内存里参与派生，派生出的数据密钥按 SDK 设计保存在 `localStorage`（这与 store.js 本机明文存放同级，未新增暴露面）。

## 6. 为什么不用 BaaS / 为什么不做 CRDT

| 选项 | 否决理由 |
|---|---|
| **Firebase / Supabase** | 数据需明文入库才能用其查询能力 → 破坏零知识承诺；Supabase 可 RLS+pgcrypto 部分补救，但 Firebase 基本无解 |
| **LeanCloud / 各类 BaaS** | 同类问题 + 数据归属不透明 + 按量计费在同步场景下易失控 |
| **邮箱/短信/OAuth 登录** | 每一项都要第三方服务或额度，注册不再免费；且邮件/短信本身就是隐私面。纯令牌模式把这部分成本和风险一起消掉 |
| **自研 CRDT/OT** | 单用户多设备、无并发协作场景，`base_rev` 乐观并发已足够 |
| **直接把 localStorage 打包上传** | 会带上 API Key 和 PIN 哈希，绝对不行 |

若**未来要做「命理师代客起盘」多端协作**，再评估 Yjs + 服务端 relay，届时数据模型不变（仍是密文 blob）。

## 10. AI 云代理（P4 落地）

这是**唯一一处明文离开用户设备的路径**，所以单独一节讲清楚它保什么、泄什么、限什么。

### 10.1 两条 AI 链路

| | 云代理（推荐） | 自带 Key 直连 |
|---|---|---|
| 用户要做什么 | 什么都不做 | 在「模型配置」里填 Key |
| 密钥在哪 | 服务端加密落库 / 进程内存 | 只在本机 localStorage |
| 谁能看到提问内容 | 服务端（转发必需）+ 模型服务商 | 仅模型服务商 |
| 限额 | 服务端强制：每日 N 次 + 每分钟 M 次 | 无（由用户自己 Key 的余额决定） |
| 适用 | 用户没有自己的 Key | 用户已有 Key，或额度用完 |

客户端在 `js/ai.js` 里做**择优路由**：云会话可用且服务端已配置 → 走云代理；否则走用户自带 Key；两条都不可用 → 本地规则化解读（离线兜底，`isDemoMode()` 已按此改写）。

### 10.2 服务端 Key 保管

```
AI_SITE_KEY（env，进程内存，优先）
        └─ 未配 → ai_proxy_config 表里用户的 Key（AES-256-GCM 密文，AI_KEY_MASTER 派生密钥）
```

- `AI_KEY_MASTER`：32 字节主密钥，**只存在于环境变量**。不落库、不打日志、不进任何接口响应。换了它，已存 Key 密文全部作废（`ai_key_unreadable`）。
- 明文 Key **永不出现在任何接口响应里** —— `GET /v1/ai/config` 只回 `site_key_available:boolean` 与 `site_key_preview`（前几位掩码）。
- `lib/aikey.js` 负责加解密，`lib/sitekey.js` 解析 env 里的 `protocol://key@base-url/model`（`|` 分隔多把轮询）。
- 多把内置 Key 轮询，分摊单 Key 的限流压力。

### 10.3 限额与限流（用户明确要求的）

`lib/ailimit.js` + `lib/ratelimit.js`，顺序固定为**先分钟限流、后记每日额度**：

| 层 | 默认值 | 打满后 |
|---|---|---|
| 每分钟 | 6 次 | `429 rate_limited`（带 `retry_after`） |
| 每日 | 30 次 | `429 daily_limit_reached`（`ai_usage` 表按 UTC 日滚动，**不额外扣减**） |

超限时**不回退到用户自带 Key**：客户端 `callLLM` 把 `daily_limit_reached / rate_limited / ai_not_configured / ai_proxy_disabled` 判为"终态错误"，直接把汉化文案抛给用户，避免换个姿势再失败一次。

### 10.4 错误码契约（不透传上游原文）

上游任何报错都被服务端归类为固定错误码，客户端 `friendlyProxyError()` 映射成中文文案。上游原文、Key、堆栈**一律不回传**，避免把服务端配置细节泄漏给调用方。

| 错误码 | HTTP | 客户端文案方向 |
|---|---|---|
| `ai_proxy_disabled` | 503 | 站长未开启，改用自己 Key |
| `ai_not_configured` | 409 | 站长未提供 Key，引导填自己的 |
| `daily_limit_reached` | 429 | 今日已用完，明天 0 点恢复 |
| `rate_limited` | 429 | 操作太快，稍等几秒 |
| `upstream_timeout` / `upstream_unreachable` | 504 / 502 | 稍后重试 |
| `upstream_too_large` | 502 | 返回过长，把问题问具体 |
| `upstream_bad_shape` / `upstream_empty` | 502 | 重试 |
| `upstream_unauthorized` / `upstream_not_found` | 502 | 请站长检查 Key / 模型名 |
| `upstream_rate_limited` | 429 | 云端 Key 被限流 |
| `upstream_error` / `upstream_rejected` | 502 | 稍后重试 |

未知错误码走兜底文案，**不泄漏服务端原文**（有测试锁定）。

### 10.5 合规提示（上线前必读）

把一把 Key 分享给不特定用户，**可能违反模型服务商的 ToS**（多数条款禁止转售/共享 API 访问）。上线前请确认：

- 服务商条款是否允许为你的用户代发请求；
- 若不允许，把 `AI_PROXY_ENABLED` 保持 `false`，走"用户自带 Key"链路（功能完全正常，只是需要用户自己填 Key）；
- `AI_DAILY_LIMIT` / `AI_RATE_PER_MINUTE` 同时是**成本护栏**：它们决定你这把 Key 一天最多被打掉多少额度。
